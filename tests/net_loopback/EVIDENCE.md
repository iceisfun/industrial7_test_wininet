# net_loopback / harness: the "first HTTPS request returns 12030" flake (flake12030)

Win10 22H2 VM (local QEMU, no network, no DNS server), HKCU `CertificateRevocation=1`, autodetect=1. Probe: `tests/probe_first_https`.

## Cause (client-side first-use latency, turned into a failure by our server's 5 s timeout)
| Finding | Evidence |
|---|---|
| The client sends its ClientHello at once; the server reads it (event `HS_BYTES 158`, ~30 ms after ACCEPT). The stall is AFTER the ServerHello: the client's next flight is late, so the server's handshake `recv` hit its 5 s `io_timeout_ms` (`TIMEOUT recv timeout`, `TLS_ABORT handshake recv=-1 round=1`), closed, and wininet returned 12030 when it finally continued. It is not "no ClientHello within the io timeout" as first guessed (events are `ACCEPT`, `HS_BYTES`, then `TIMEOUT`, round=1 means round 0 succeeded). | `docs/research/flake12030/probe_prefix_5s_sampler_boot1.txt` |
| The client thread is inside `wininet!ServerCertCheck -> WINTRUST -> crypt32 chain build -> cryptnet` (sampler: main thread stack wininet+0xc3a15 -> WINTRUST -> crypt32 -> cryptnet); a cryptnet worker is in `winhttp` and another thread in DNSAPI/RPCRT4 (DNS client RPC). | same file (SAMPLE 800ms / 2500ms) |
| What it fetches: crypt32 "Automatic Root Update" for the untrusted self-signed root: `http://ctldl.windowsupdate.com/msdownload/update/v3/static/trustedr/en/authrootstl.cab` and `.../disallowedcertstl.cab`, timeout PT15S, `Call_WinHttpSendRequest` error 0x2EE7 (12007 name not resolved). CAPI2/Operational events 19/20/52/53 (keywords "Retrieval, Automatic Root Update"). | `docs/research/flake12030/probe_capi2_events_boot1.txt` |
| Duration: the DNS failure takes 7-8 s (12.4-12.7 s in the first child after a boot: two names / first DNS client use). It is then cached for a few seconds, so ~1 fresh process in 8-10 is slow and the others take 60-100 ms; a slow one shows up every ~12 s in a loop of fresh processes. A fast run is the normal case, which is why the same test passes in one boot and fails in the next. | probe1 (8 boots) |
| Switching the fetch off removes the stall: policy `HKLM\SOFTWARE\Policies\Microsoft\SystemCertificates\AuthRoot\DisableRootAutoUpdate=1` gave 0 failures and no 7-13 s children in 3 x 40 fresh processes; the same boots without the policy (before and after) failed 8 + 8 of 240. | `probe_AB_policy_prefix_boot2.txt` (A/B/C blocks) |
| Not the cause: listen backlog, accept race, Nagle (TCP_NODELAY is set), server cred init (srv_start 90-250 ms), schannel client credential warm-up (`warmschan`: no change), `SECURITY_FLAG_IGNORE_REVOCATION` (`ignrev` children: no failure seen in 10 + 20 runs, but too few to separate from the ~10 % base rate; the CAPI2 trace shows the fetch is root auto-update, not CRL), first-use after boot as such (the first child of a boot was only slower, 12.4-12.7 s, probably a cold DNS client; not tested further). |

Numbers (fresh process = one `--child fh`: srv_start, one HTTPS GET with IGNORE_UNKNOWN_CA, stop):
- before the fix, server io timeout 5 s: probe1 592 children over 8 boots, 49 failed with 12030 (8.3 %), failures took 5.9-12.7 s; probe2 A/C blocks 240 children, 16 failed; in all 8 boots the first failure was among the first 4 children (the very first child in 6 of them).
- with the handshake timeout raised (below): probe4, 4 boots x 120 children = 480, 0 failed; slow ones (7-13 s) still happen and now succeed.
- with `DisableRootAutoUpdate=1` the stall is gone on the client too (probe2 B: 0 slow-DNS children in 120), but this is a guest OS policy and is NOT applied by the harness.

## Fix (our side)
- `common/srv_tls.c`: the TLS handshake of `srv_tls_accept` runs with a 30 s socket timeout (`SRV_HANDSHAKE_TIMEOUT_MS`) instead of `io_timeout_ms`, restored after the handshake. The stall is the client's, not ours; the server just must not give up. srv_stop and lifetime still end it.
- plaintext HTTP sent to the TLS server: schannel calls the partial record "incomplete" and waits, so `tls_broken_http_to_https_server` (12152) had relied on the old 5 s timeout expiring just before the client's 5 s receive timeout. The server now aborts at once if the first byte is not 0x16/0x80 (`TLS_ABORT not a TLS record (first byte 0x47)`), which gives the same 12152 deterministically.
- `tests/https_tls/tls_pki_util.c` has its own mini TLS server (`mts`) with the same 5 s timeout: now 30 s for the handshake, 5 s after it. One remaining `tls_pki_trailing_dot_host` 12030 in the 10-boot run was this.
- New event `SRV_EV_HS_BYTES` (first handshake bytes read) and the probe `tests/probe_first_https` (fresh-process children, timeline, stack sampler, CAPI2 log dump, policy A/B).
- Removed the 12030 retries/downgrades: `bio_https_get` (http_body_io), `rs_limits.c` first-HTTPS retry (http_redirect_status), `wire_extra.c` 5-attempt loop (http_request_wire), and the `ERROR_INTERNET_CONNECTION_ABORTED` arm of the transient-retry in `tls_util.c/.h`, `tls_info.c` (2), `tls_combined.c`, `tls_certerr.c` (3), `tls_pki_util.c`, `tls_async.c`. The `ERROR_INTERNET_CONNECTION_RESET` arms stay (a different error; no `transient` note fired in the 10 boots either, so they are dead weight but not proven wrong).

## What Win10 does (for the record)
On a machine without DNS/network the first (and every ~10 s) TLS handshake to a server whose certificate chains to an unknown root blocks the calling thread in `wininet -> WinVerifyTrust -> CertGetCertificateChain` for the length of the resolver failure of `ctldl.windowsupdate.com` (7-13 s here), before the client's Key Exchange flight is sent. An IGNORE_UNKNOWN_CA request does not avoid it: the chain engine fetches before wininet applies the flag. The connect/send/receive timeouts of the session (5 s in `t_inet_open`) do not cover it (the thread is in crypt32, not in a socket call).
